## The project to build

### **SettleSense: AI-Verified Payment Reconciliation Controller**

**One-line pitch:**

> An explainable, human-in-the-loop finance controller that reconciles Razorpay payment/settlement records against bank and merchant ledger entries, auto-resolves high-confidence matches, identifies settlement breaks, and generates actionable exception cases with evidence.

This is not merely an LLM chat interface over CSV files. It is a complete **verification pipeline**:

```text
Synthetic Razorpay payments + settlements
                +
Synthetic merchant ledger / bank-statement records
                |
                v
     Normalization and feature extraction
                |
                v
  Deterministic candidate generation / blocking
                |
                v
   Hybrid match engine: rules + fuzzy scoring
                |
                v
Confidence-calibrated decision controller
        |                         |
        v                         v
Auto-match                    Exception queue
        |                         |
        v                         v
Reconciliation report     AI investigation summary
        |                         |
        +------------> Immutable audit trail
```

The central insight: **AI should explain uncertain financial cases, not blindly decide money outcomes.** The deterministic reconciler does the high-confidence matching; an LLM or lightweight AI layer classifies ambiguity and writes structured investigation summaries. Any payout/refund/ledger adjustment remains a simulated and approval-gated action.

That directly mirrors Razorpay’s stated preference for verification capacity, exception management, trustworthy workflows, and appropriate AI judgment.[^2_1]

## Exact scope: do not overbuild

Your goal is not to build an enterprise ERP. Your goal is a narrow, complete finance-control loop that runs reliably and makes the reviewer confident you can build production systems.

### The finance loop

1. Ingest three sources of synthetic records:
    - Payment gateway transactions.
    - Razorpay-style settlement records.
    - Merchant bank ledger / accounting ledger entries.
2. Normalize:
    - Amounts in paise.
    - Timestamps to UTC/IST consistently.
    - Payment IDs, order IDs, bank references, UTR-like references.
    - Merchant, payer, method, status and settlement dates.
3. Generate candidates:
    - Match via exact payment/order/reference IDs first.
    - Use blocking on amount, date window, merchant ID and payment method.
    - Avoid $O(n^2)$ naive comparison across every record pair.
4. Score candidates:
    - Exact-ID score.
    - Amount agreement.
    - Timestamp/settlement-date distance.
    - Text/reference similarity.
    - Merchant/entity consistency.
    - Status consistency.
5. Decide:
    - **Auto-match** only if score exceeds a strict threshold and the margin over the next candidate is safe.
    - **Review** when competing candidates are close or fields disagree.
    - **Unmatched** when no reliable candidate exists.
    - **Potential duplicate** where many ledger entries map to one payment, or vice versa.
6. Explain:
    - Produce a structured explanation for every decision.
    - Generate a concise AI explanation only for uncertain exceptions, grounded in the structured facts.
    - Never let the LLM produce unverified arithmetic or alter match decisions without constraints.
7. Report:
    - Match rate.
    - Precision / recall / F1 against synthetic ground truth.
    - Auto-match coverage.
    - Exception count and breakdown.
    - False-match financial exposure.
    - Time taken / records per second.
    - A downloadable exception CSV.

## Synthetic dataset design

Do **not** make a perfectly clean synthetic dataset. That would look weak and fail Razorpay’s “honest exception list” expectation.[^2_1]

Create 200–500 payments with a hidden `ground_truth_match_id` only used by the evaluator. Transform the records across sources so reconciliation is realistic.


| Case type | Suggested share | Example |
| :-- | --: | :-- |
| Exact matches | 45% | Same payment ID, amount, and settlement date |
| Benign formatting differences | 15% | `PAY-0001` vs `pay_0001`, casing/spaces/reference prefixes |
| Date-delayed matches | 10% | Settlement appears T+1 / T+2 from payment |
| Partial / fee-adjusted matches | 8% | ₹1,000 gross payment, ₹982.30 settlement after fee/tax |
| Duplicate ledger entries | 7% | One payment appears twice in merchant ledger |
| Amount mismatch | 5% | Wrong amount, refund, partial payment, manual adjustment |
| Missing counterpart | 5% | Payment exists but bank/ledger record missing |
| Ambiguous candidates | 5% | Same amount/merchant/date, weak identifying attributes |

The key is to seed a deterministic random generator so the dataset is reproducible. Keep the ground truth private from the matching pipeline, then evaluate automatically after every run.

For a finance workflow, **precision matters more than coverage**. A wrong automatic match can corrupt books; an unresolved case can be escalated to a human. Say that explicitly in the video.

Useful metrics:

$$
\text{Precision} = \frac{TP}{TP + FP}
$$

$$
\text{Recall} = \frac{TP}{TP + FN}
$$

$$
F1 = 2 \times \frac{\text{Precision} \times \text{Recall}}
{\text{Precision} + \text{Recall}}
$$

Also report a finance-specific metric:

$$
\text{False-match exposure}
= \sum_{\text{incorrect automatic matches}} |\text{matched amount}|
$$

That metric will make your submission feel financially mature. A system with a high match rate but high false-match exposure is dangerous; that is a much stronger story than merely claiming “95% accuracy.”

## Where AI genuinely belongs

The challenge will likely receive many projects that put an LLM on top of a CSV. Do not do that.


| Component | Preferred technique | Why it is credible |
| :-- | :-- | :-- |
| Exact matching | Deterministic rules | Fast, transparent, reliable |
| Candidate blocking | Amount/date/entity filters | Prevents noisy comparisons and supports scale |
| Fuzzy reference matching | RapidFuzz / string similarity | Handles real formatting variation |
| Candidate scoring | Weighted interpretable score or calibrated classifier | Produces auditable decisions |
| Exception categorization | Rules first; constrained LLM as optional layer | Keeps financial logic deterministic |
| Exception narrative | LLM with JSON-constrained input/output | Good use of AI for language/reasoning |
| Analyst Q\&A | Retrieval over canonical records | Useful secondary feature, not core system |
| Money action | Simulated only, approval gated | Safe and appropriate |

A strong phrasing for your pitch:

> “The system does not use an LLM to reconcile money. It uses deterministic and calibrated matching for financial truth, then uses AI to turn exceptions into analyst-ready investigation summaries. The model is not the source of truth; the auditable record is.”

That is exactly the sort of **AI judgment** Razorpay says it is evaluating.[^2_2][^2_1]

```text
    +-- Exception classifier
    +-- Audit logger
    +-- Metrics evaluator
    |
    +-- PostgreSQL or SQLite for 5-day build
    +-- CSV generator + ground-truth evaluator
    +-- Optional LLM provider / local model for exception summaries
```


### Recommended implementation choices

- **Backend:** FastAPI, Pydantic, Pandas or Polars, SQLAlchemy.
- **Storage:** SQLite if deployment speed matters; PostgreSQL only if it is already comfortable for you.
- **Matching:** exact IDs → normalized reference exact match → blocked fuzzy candidates → weighted scoring.
- **Frontend:** a focused dashboard, not a broad product:
    - KPI cards.
    - Reconciliation run control.
    - Records table with outcome labels.
    - Exception queue.
    - Evidence drawer / audit timeline.
    - Accuracy and match-rate charts.
- **Observability:** structured JSON logs, reconciliation-run ID, timing per pipeline stage, decision reason codes.
- **Deployment:** Docker Compose + Render/Railway/Fly.io/Vercel as appropriate. The repo must run locally with one clear command.

Razorpay’s own documentation supports test-mode API keys, test transactions, payment links, subscriptions, and webhook-based event handling, so an optional test-mode integration is feasible if you finish core reconciliation early. But it is **not** required for Track 04. Do not sacrifice evaluation rigor to chase external integration.[^2_3][^2_4][^2_5][^2_6][^2_7]

## The killer demo scenario

Use one end-to-end flow in the video:

1. Upload or generate a 300-record batch.
2. Show that payments, settlements, and bank records contain real-world messiness: timing delay, formatting drift, duplicate entries, missing records, fee differences.
3. Run “Reconcile batch.”
4. Show results:
    - 240 auto-matched high-confidence records.
    - 32 review-needed cases.
    - 18 unmatched cases.
    - 10 duplicate/multi-match warnings.
5. Click an exception:

```text
Payment: pay_1043

Likely reason: payment gateway fee + tax adjustment
Decision: Needs finance approval
Confidence: 0.79
```

6. Demonstrate that an attempted action such as “create adjustment” is **approval-gated**.
7. Show the immutable audit trace:
    - input hashes,
    - candidate set,
    - features,
    - score,
    - decision,
    - reason code,

8. End on the metrics page and exception CSV.

This is demonstrably more compelling than a chatbot because it proves data engineering, reliability, core matching logic, UI product thinking, explainability, and safe action design.

## Five-day execution plan

You have five days, so build in vertical slices. A fully functioning narrow pipeline beats a broad half-built multi-agent system.


| Day | Non-negotiable outcome | Deliverables |
| :-- | :-- | :-- |
| **Day 1** | Define the loop and build reproducible data | Data schema, 200–500 synthetic rows, ground truth, canonical model, README skeleton |
| **Day 2** | Deliver reconciliation v1 | Exact matching, candidate blocking, fuzzy references, scoring, automatic metrics |
| **Day 3** | Build the exception controller | Exception categories, explanation templates, audit records, reviewer approval simulation |
| **Day 4** | Build product UI and deployment | Dashboard, exception table, evidence drawer, Docker, deployed link |
| **Day 5** | Harden and submit | Tests, metrics screenshots, README, architecture diagram, 5‑minute video, failure story |

### Day 1: Lock scope and data

- Write the problem statement in one paragraph.
- Create `payments.csv`, `settlements.csv`, `bank_ledger.csv`, and a hidden `ground_truth.csv`.
- Build one command that regenerates all datasets deterministically.
- Define all error classes up front.
- Start your README immediately. Do not write it at 3 AM on deadline day.


### Day 2: Build the evaluation core

- Implement normalization.
- Implement candidate generation and deterministic scoring.
- Auto‑evaluate against hidden ground truth.
- Produce a JSON/CSV output containing `matched`, `review`, `unmatched`, `duplicate`.
- Target a real baseline first; do not tune metrics in secret.


### Day 3: Add trust and workflow design

- Build audit logs.
- Add explicit reason codes such as `EXACT_PAYMENT_ID`, `AMOUNT_DATE_REFERENCE_MATCH`, `AMBIGUOUS_CANDIDATES`, `NO_COUNTERPART`, `FEE_ADJUSTMENT_SUSPECTED`.
- Add structured exception summaries.
- Add the approval-gated simulated adjustment workflow.
- Optional: connect an LLM only after the deterministic pipeline is finished.


### Day 4: Productize

- Ship the UI.
- Add a “Run Reconciliation” button and seeded scenario selector.
- Build the exception queue and record evidence view.
- Dockerize and deploy.
- Test the whole workflow from a clean clone.


### Day 5: Make it reviewable

- Add 10–15 focused tests.
- Add a failure injection mode: corrupted CSV, missing columns, duplicate payment IDs, model/LLM unavailable.
- Record metrics on a frozen evaluation dataset.
- Record your demo in one smooth take.
- Write the “What broke and how you got out” response honestly.

## The “what broke” answer

Do not invent drama. A strong answer could be:

> “The initial matcher over-relied on amount and date. In data containing repeated ₹999 and ₹1,499 transactions, it produced false auto-matches—the most dangerous error for a finance controller. We fixed this by adding entity/reference blocking, a top-two candidate score margin, and a strict confidence gate. Cases below the threshold now enter the exception queue rather than being force-matched. This reduced auto-match coverage, but improved precision and reduced false-match exposure. The product is deliberately optimized to escalate ambiguity instead of manufacturing certainty.”

That answer proves engineering maturity, safety judgment, financial reasoning, and honesty. It is likely much more valuable than claiming “everything worked.”

## 5-minute pitch structure

**0:00–0:30 — Hook**\
“Finance teams lose time and trust reconciling payments, settlements, and bank entries because the records disagree in small but expensive ways.”

**0:30–1:05 — Why this matters**\
“Automation cannot blindly match financial records. One false positive can corrupt the books, while unresolved exceptions overload operations teams.”

**1:05–2:00 — Live product demo**\
Upload/run a 300-record batch and show dashboard outcome numbers.

**2:00–2:55 — Explain the reconciliation engine**\
Exact matches, candidate blocking, fuzzy references, confidence thresholds, and human-review routing.

**2:55–3:40 — Explain responsible AI use**\
“Deterministic logic decides financial matches; AI translates uncertain cases into grounded investigation summaries. No LLM is allowed to invent, mutate, or autonomously execute ledger adjustments.”

**3:40–4:15 — Metrics**\
Show match rate, precision, recall, F1, false-match exposure, throughput, and unresolved-exception taxonomy.

**4:15–4:45 — Failure recovery**\
Show malformed input/error handling and the initial false-match issue you corrected.

**4:45–5:00 — Finish**\
“SettleSense turns reconciliation from manual spreadsheet triage into an auditable finance-control loop: match what is safe, explain what is uncertain, and escalate only what needs a human.”

## Strict cut list

Do **not** spend your five days on:

- A full multi-agent architecture just to say “agents.”
- Fine-tuning any model.
- Fancy Kafka infrastructure unless it already exists and costs nearly zero time.
- OCR or real bank statement parsing as the central scope.
- Building an entire accounting system.
- Live money movement.
- A broad chatbot.
- Auth, multi-tenancy, billing, role-management, email systems.
- Pixel-perfect UI before core metrics and exception handling work.

If time remains, the first stretch enhancement is **Razorpay test-mode payment/subscription webhook ingestion**: test environments permit dummy transactions with no real money, test-mode API keys, and test webhooks for event notifications. Use it only to make the demo feel more connected to the ecosystem; it should not replace the required 50+ record batch evaluation.[^2_4][^2_6][^2_7][^2_3][^2_1]

## Final call

Pick **AI Finance Controller** and build **SettleSense**—an explainable reconciliation and exception-management system with measurable performance, strong auditability, and properly bounded AI.

It will let you show the exact combination Razorpay is signaling for: real problem taste, reliable build quality, sensible AI use, measurable outcomes, and honest failure handling. It also plays directly to your existing financial-compliance background, so your architecture and explanations should be much more credible than someone starting from zero.[^2_2][^2_1]
